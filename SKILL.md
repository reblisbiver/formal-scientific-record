# Formal Scientific Record — Scientific Compiler (Stage-2 candidate 0.6.2)

**Input:** one user-specified `SOURCE_DIR` only. `OUTPUT_DIR=SOURCE_DIR/fsr_record` by default. Read the provided folder recursively, excluding any prior `fsr_record`, `formal_report`, `report.pdf`, generated report documents and archive caches. Do not read other projects. Never execute scientific experiments, training, simulation, evaluation jobs or change source evidence.

**Authoritative locked reference:** `references/BASELINE_v1.1_LOCKED.md` and the three approved LaTeX exemplars in `references/`. Their corresponding PDF files and known plotting blemishes are frozen in the user's Formal Scientific Record Library benchmark archive; do not rewrite the baseline or exemplars. The exemplars show style and distinct compositions, NOT a universal section sequence, and synthetic exemplar numbers must NEVER appear in a real report. Output scientific reports entirely in English; conversation with the user remains Chinese.

## Science and minimal completeness — hard requirements

The assistant is a **compiler of recorded scientific facts, not a scientific author**.
- Zero new hypotheses, interpretations, explanations of implications, recommendations, causality claims, or conjectures. No claims extrapolated beyond source evidence; no filling missing values. Only: term definitions, recorded research questions, conditions and exceptions, recorded methods, measurements/results and deterministic calculations, explicit validity/missing states.
- Primary goal: **minimal complete representation** of all source-recorded research questions, without requiring the reader to inspect underlying files to understand the question, model, variable/target, conditions, denominator/units, observed result and verification status when relevant. Do not equate full logs with main-text completeness.
- Scientific objects are selected and ordered by dependencies and questions, NOT a rigid 'specification-hypotheses-results' form. Scientific units: definitions / assumptions / questions / methods / hypotheses (only if pre-recorded) / observations / verification / scope. No required empty sections.
- **Optional hypothesis typography:** when explicit source hypotheses have multiple clauses, render them as separate, indented, italicized propositions with stable bold labels (for example H1(a), H1(b), H2). Match those labels to grouped verification rows with prominent bounded-status phrases. The renderer supports opt-in text fields presentation=hypothesis, hypothesis_group, group_title, hypothesis_marker (a/b), and table presentation=hypothesis_status. These are display metadata only; keep all source statements, evidence, and the scientific relation map complete. Do not force this format onto reports without hypotheses or invent acceptance criteria.
- **Source-recorded hypothesis closure (conditional, not a fixed template):** when an original project contains explicit study hypotheses or prespecified directional expectations, treat each as a source-recorded scientific claim that must be retained in the MAIN readable report, not silently relegated to source appendix merely because the measurement and result rows are present. For each hypothesis, preserve its actual predicate/conditions and map source hypothesis -> testable observable/metric -> saved observation -> source-grounded evaluation status. Put these in the reading order allowed by their dependencies: define symbols before use, state a hypothesis before the observations that evaluate it, and place its bounded evaluation at or after those observations. The evaluation can be a compact hypothesis/status table or inline outcome, not a new generic conclusion section. Use only recorded acceptance/rejection rules where available. If no explicit test or decision rule exists, report exact descriptive checks and mark formal adjudication NOT ESTABLISHED instead of declaring supported/rejected; if required data were unavailable, say NOT TESTED. A compound hypothesis may have an observed component and an unverified component, so do not compress partial evidence into blanket confirmation. If there was no recorded hypothesis, do not invent one or add placeholder text. Stage 1 must explicitly look for hypothesis statements in original protocols/specifications; Stage 2 deletion/coverage review must fail scientific signoff if one remains only in the appendix or if its test-status connection is absent.
- **Mechanism-first formality (algorithmic reports):** when a comparison depends on an algorithm, controller, optimizer, decision rule or sequential update, identify the **decisive computational recurrence/state transition/selection/aggregation/backup** before deciding which result differences merit a displayed equation. Read implementation or precise source audit, not just names of algorithm components. If code supports an exact update, place that minimal equation (or equivalent typed pseudocode) in the main text with units, denominator, state and symbol definitions. If a unique equation is not source-supported, describe the verified transition and its missing pieces explicitly; never invent textbook updates. Check against code with bounded synthetic arithmetic when feasible, and attach evidence locators. For MCTS planning, separate sampled path return, leaf/tail evaluator, horizon normalization, visit/return-sum update, and final action statistic when recorded. A simple observed metric subtraction is secondary unless it is itself the research question. In the deletion test, remove the update while keeping the result table: if methods are then indistinguishable, the update was mandatory.
- **Promotion rule:** main text contains research object/input/output, manipulated factors, conditions changing comparability, denominator/analysis unit, metric definitions, observed key comparisons and uncertainty/bounds if available. Merely reproducibility-level hyperparameters, raw logs, machine IDs, paths, hashes, full tables, source pointers and source inventory go ONLY in the final appendix and machine JSON.
- **Single-question comparison compression gate:** main text should contain (i) a compact design and manipulated variables, (ii) primary metric definitions with unit/denominator, (iii) one paired result table, (iv) an evidence-driven plot only if useful, and (v) a short source-grounded validity boundary. Do NOT enumerate all sessions per fold, unchanged hyperparameters, training logs, stage metrics or subgroup profiles unless the original research question explicitly requires them. Put secondary scientific details in record.json at tier=appendix, keeping the main body concise. Target one or two readable pages; if more are necessary, state the specific coverage requirement in QA instead of padding or omitting mandatory science.
- **Compression means deletion of redundancy, not definitions:** a defining equation and symbol line replaces repeated prose. State shared conditions once; do not repeat tables as charts without independent purpose. The validator enforces a bounded prose/table budget for one-question comparisons.
- **Visualization-preservation review:** for three or more comparable paired folds, seeds, participants, or stages, actively assess whether a sourced zero-centered difference plot conveys a distinct necessary view of direction or heterogeneity. Retain such a plot in the final PDF when it contributes scientifically; do not discard it merely for brevity. If the exact table already makes the comparison fully transparent, document the rationale for omitting a separate chart in QA, not in the human-facing body. Content-only Stage-2 trials may record a figure need/specification but do not need to render one. Where formulas have >=4 symbols, define terms clearly once. Do not cram tables or lose readability to meet a page target.
- Provide explicit formal variables and equation/objective definitions when source supports them. Define symbols at first occurrence; do not present invented formulas as source-authored formulas. Source-grounded deterministic definitions such as Δ=treatment−baseline are permitted if labeled as derived definitions. Require mathematical precision without unnecessary prose.
- Only label a hypothesis preregistered when a verifiable pre-result source establishes that status (a timestamp alone is insufficient). Ordinary descriptive questions need no missing-preregistration sentence; report a missing rule only if it changes the interpretation of a source-recorded decision. Never invent a threshold. Verification verdicts require explicit pre-existing rule and matching metric/analysis unit; descriptive differences are NOT statistical significance.
- For every observed value disclose correct unit, denominator, grouping and aggregation. Do not silently aggregate incompatible folds, trials, seeds or participants. A chart is made from actual numerical CSV input, not model-imagined arrays.
- **Scientific-object grounding:** a Bernoulli-like scoring formula does not itself prove that stored target values are binary or identify what label 1 means. A feature name does not specify its functional construction; a named training loss mode is not its mathematical objective. Extract supported definitions or mark a bounded missing definition once. Never present an assumption as a verified source fact. Keep production-mechanics descriptions in machine QA, not the reader-facing scientific body.
- Preserve source facts and source disagreements explicitly; expose necessary scientific caveats in a compact main 'Scope' subsection when they affect interpretation of the measurement. All record locators and audit metadata go in the appendix.
- All artifacts are produced only under OUTPUT_DIR, except this Skill is itself managed separately by the user. Do not mutate source data or the locked benchmark.

## Execution procedure — four checkpoints, no added agents

Read `references/BASELINE_v1.1_LOCKED.md`, `references/COMPOSITION_PROTOCOL.md`, and `references/QA_CONTRACT.md`. Resolve scripts relative to this Skill path. Ignore every prior `SOURCE_DIR/fsr_record` as input to the science; existing outputs are not source evidence. Work only within the supplied SOURCE_DIR and Skill resources.

**Stage 1 / Scientific Extraction → source-fidelity checkpoint.** Independently compare the original scientific sources against the final selected claim inventory, not just an inventory derived from the generated report. For each recorded question, verify that the essential definitions, conditions, measurements, results and source-status boundaries have a main-text representation or justified appendix placement. Test at least one plausible source-backed deletion; if this source-first review is not completed, disclose that boundary rather than treating structural validation as scientific coverage. Read original project material recursively and identify source-recorded scientific question(s), variables, experimental conditions, definitions, known results and missing states. Every scientific fact needs its original source path and locator. Separate recorded facts from arithmetic computed from saved data. No report prose yet. If no coherent source question can be recovered, record that limit rather than inventing one.

**Stage 2 / Scientific Composition → relation-coverage checkpoint.** Before writing natural-language paragraphs, establish a small `composition_audit.json` using the `relation-map-v1` schema from `references/COMPOSITION_PROTOCOL.md`. For each recorded research question, select the smallest complete set of sourced *scientific relations* (definition, constraint, contrast, model, objective, measurement, observation, verification or scope). State prerequisites and match each relation to an exact scientific expression in `record.json` (equation, table, figure or minimal condition prose). Do not reuse a generic statement as a substitute for a source-grounded relationship. Equations are preferred only when the source licenses an exact relation; non-mathematizable procedures remain concise prose. Organize by scientific dependencies, **not** a fixed chapter sequence.

Generate the content-only scientific draft and check the relation mapping **before** any PDF:
```sh
python3 scripts/build_draft.py OUTPUT_DIR/record.json --audit OUTPUT_DIR/composition_audit.json --output OUTPUT_DIR/body_draft.md
python3 scripts/check_composition.py OUTPUT_DIR/record.json OUTPUT_DIR/composition_audit.json
```
Read `body_draft.md` as a researcher would: can each source question be answered, are conditions/denominators defined, do definitions precede their uses, and could any phrase or figure disappear without loss of unique information? Fix the scientific content first; do not pad the audit with prose justifying choices. A structural PASS is not proof of semantic correctness.

**Stage-2 scoped trials (when explicitly requested):** limit the source scan to the nominated question and source files, and produce the standalone `relation_plan.json` instead of a full `record.json` / PDF. Apply the relation-selection, atomicity, and true-prerequisite tests in `references/COMPOSITION_PROTOCOL.md` and `scripts/check_relation_plan.py`. Treat plan validation as structural diagnostics, not a science-quality PASS. A complete FSR run still uses the source-to-relation-to-expression map.

**Stage 3 / Scientific Verification → numeric/scope checkpoint.** Reaggregate saved measurements with bounded scripts when possible (never rerun model training or scientific experiments). Verify source-grounded equations, units, denominators and contrasts only as far as the available data permits. Save `numeric_audit.json`, bound to the current `record.json` SHA-256, with exact scope and limitations according to `references/QA_CONTRACT.md`. For **new** complete runs with displayed scientific metrics, also create `metric_registry.json` using the supported contract in `references/QA_CONTRACT.md`: register every displayed metric with its source/definition, provenance hash, scope, checked or source-only status, and question-linked result inventory. Its metric IDs must match the report projection, declarations and registry entries; do not convert absence to zero or source-defined semantics into numeric reaggregation. Older reports without a registry retain their previous status when unchanged. Original research acceptance, full model rerun and unavailable source experiments are separate informational facts, not FSR failure gates.

**Stage 4 / Scientific Publication → final-artifact checkpoint.** Run `scripts/render.py` against the validated `record.json`, compiling a professionally typeset English LaTeX PDF. Run `scripts/verify.py` for PDF mechanics and fallback page rasterization. Actually inspect every final page, including appendix, at legible zoom. Check typography, figures, units, consistency and pagination against the frozen examples (without copying their chapter structures). If relationships remain unclear or content redundant, return to Stage 2; if numeric facts are wrong, return to Stage 3. Never manually patch the generated TeX. Save `visual_qa.json` bound to the final PDF hash and run `scripts/finalize.py OUTPUT_DIR` LAST. Only `final_status.json` is authoritative about artifact completion.

Respond in Chinese with exact PDF/TeX/record/QA/final_status paths, verified stages and limitations. Do not claim scientific acceptance, universal validity, or human approval based on program tests. The report itself remains English.

## Anti-regressions

- Main PDF must not contain JSON paths, hashes, record IDs, file inventory, code dumps or source listings before the Appendix.
- No filler introductions, 'the results suggest', 'future work', 'implications', prose conclusions, invented hypotheses or pre-registration.
- No force-fit of a theory note into an experiment results page, and no mandatory figures when numerical data are absent. Results with two or more directly comparable groups or repeated axes should ordinarily use a useful chart in addition to compact numbers when it adds independent readability.
- Use prose only for facts or conditions that cannot be expressed more compactly as source-grounded equations, a comparison matrix or aligned observations; do not turn scientific constraints into semicolon-packed paragraphs.
- No claim of metric validation if only PDF rendering validated; distinguish arithmetic reaggregation from original-model reruns and source-research scientific acceptance.
- When the original study has no registered hypothesis, omit the irrelevant default sentence about missing preregistration. Report absence only if needed to prevent an actual hypothesis/decision claim.
- A final report.tex that was manually edited after render.py is NOT reproducible or accepted. Never alter generated TeX except by changing the reusable renderer/style and regenerating the entire PDF.
- Align typography hierarchy and information density with approved frozen examples; preserve only needed scientific facts. Keep a real plot large enough to read its ticks without magnification.
